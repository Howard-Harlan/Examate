## 修复 agent 聊天页"思考/等待 AI 输出"阶段闪退

**根因**：`ChatActivity.kt` 的 agent 模式调用 `AgentOrchestrator.execute(...)`（运行在 `Dispatchers.IO`），其 `onToolCall` 回调在 IO 线程直接执行 `setLoadingStatus(status)`；而 `setLoadingStatus` 定义为 `{ loadingStatus = it }`，直接给 Compose 的 `MutableState`(`loadingStatus`) 赋值。后台线程写入 Compose 快照属非法操作，污染快照后主线程 Recomposer 在快照 apply 阶段抛未捕获 `IllegalStateException` → Activity 崩溃(force close)。普通对话模式走 `simpleChat`、且 `setLoadingStatus("正在思考...")` 在主线程调用，所以不触发；只有 Agents 模式（多步推理+工具调用）会在"正在调用…"阶段稳定复现。

**修复**（单点、最小）：将 `setLoadingStatus` 的 lambda 改为统一切回主线程写入——`setLoadingStatus = { status -> scope.launch { loadingStatus = status } }`（`scope` 来自 `rememberCoroutineScope()`，即主线程）。这样所有 `setLoadingStatus` 调用（含 IO 线程触发的 `onToolCall`）都安全。对应文件 `app/src/main/java/go/examate/hyp/ChatActivity.kt`（约第267行）。

**附**：项目里有两套聊天实现——`ChatActivity.ChatScreen`（真正在跑，本地 `mutableStateOf`/`mutableStateListOf` 自管状态）与 `ChatViewModel`（StateFlow 实现，未被引用，是死代码但线程更安全）。建议后续把活动切到 `ChatViewModel` 一劳永逸，但当前单点修复已根治闪退。

## 补充：agent 聊天"AI 回包那一刻"仍闪退的第二处根因

第一处（思考阶段 `loadingStatus` 后台写）修完后，用户实测"AI 回复时仍闪退"。定位到第二个**同类**根因：

- `ui/components/MarkdownRenderer.kt` 的 `MathWebView` 内 `MathHeightBridge`（@JavascriptInterface）在 **WebView 后台线程** 直接写 `contentHeightDp`（Compose `MutableState`），污染快照→主线程 Recomposer 抛未捕获异常→闪退。
- 触发条件：agents 模式回包含数学公式（`$$...$$`/行内 `$...$`/```tex）。因为 `AgentOrchestrator` 的 `RENDERING_PROMPT` 明确要求 AI 用 LaTeX 输出公式，agents 回包几乎必带数学块→`MathWebView` 渲染→桥回调写状态→崩在"AI 回复"那一刻。普通对话模式回包少数学，故不触发（或极少）。
- 修复：`MathHeightBridge.postHeight` 用 `Handler(Looper.getMainLooper()).post { onHeightReady(...) }` 切回主线程再写状态。
- 另：`appendAssistant` 内的记忆捕获 `maybeCaptureMemory`（主线程文件 I/O）改为 `CoroutineScope(Dispatchers.IO).launch { runCatching { ... } }`，避免主线程 I/O 隐患（其异常原本已被 `sendMessage` 的 try/catch 兜底，不会崩）。

**结论**：agent 聊天闪退是"后台线程写 Compose `MutableState`"这一类问题的两处实例（思考阶段 `loadingStatus` + 回包阶段 `contentHeightDp`），均已改为主线程写入。已重新构建 release 验证。

**排查方法沉淀**：Compose 闪退优先怀疑"非主线程写 `MutableState`"（snapshot 污染→Recomposer 抛未捕获异常）；重点排查 `@JavascriptInterface` 回调、`Dispatchers.IO` 中的状态回调、以及 `onToolCall`/`onProgress` 类回调。重组内抛出的异常不受协程 try/catch 保护。

## 修复 agent 聊天"输入后等待 AI 回复即页面崩溃"（第三类根因：WebView 重组风暴）

**现象**：每次在 Agents 聊天输入并等待 AI 回复，页面崩溃（非 force-close 异常，更像渲染进程被杀/OOM）。

**根因（与前两类不同，不是线程问题）**：
1. `ui/components/MarkdownRenderer.kt` 的 `MathWebView`/`SmilesWebView` 在 `AndroidView` 上挂了 `update = { it.loadDataWithBaseURL(...) }`。`update` 在**父级每一次重组**时都会触发，重新从 CDN 拉取 KaTeX/SmilesDrawer 并重排。Agents 回包含大量 `$...$`/`$$...$$`/`$smiles{}$`，一条消息就有几十个公式 WebView；只要 `ChatScreen` 重组，它们就全体重载 → 几十个并发脚本下载 + WebView 重排 → 渲染进程崩溃。
2. 重组风暴的触发源：`ChatScreen` 里 `loadingStatus` 在 Agents 思考/调工具阶段频繁变化 → `ChatScreen` 重组 → `items` 内每条消息的 `MessageBubble` 因 `onQuickFollowUp = { ... }` 每次都是新 lambda 实例而被迫重组 → 触发上面的 WebView 全量重载。
3. 单条消息公式数量无上限（用户说的"叠加太多内容"）：极端长回包会同时存活几十个 WebView → OOM。

**修复**（最小、低风险）：
- 删除 `MathWebView`/`SmilesWebView` 的 `update` 重载，只在 `factory` 加载一次；高度变化仅通过 `Modifier.height(contentHeightDp)` 重排，不重载页面。
- `ChatActivity.kt` 将 `onQuickFollowUp` 用 `remember { ... }` 固定为稳定 lambda，使可见气泡在 `loadingStatus` 变化时不再被迫重组（即便重组，`update` 已删也不会重载 WebView）。
- `MarkdownRenderer.kt` 新增 `MAX_FORMULAS_PER_MESSAGE = 24`：单条消息公式超过阈值时整条改用 `FallbackFormula`（等宽纯文本回退），避免极端长回包同时存活几十个 WebView。

**验证**：未跑完整 Gradle 构建（环境依赖），已静态核对所有调用点（`RenderedCodeBlock`/`ParagraphBlock` 签名加 `forceText` 默认参数，旧调用点兼容；`MathWebView`/`SmilesWebView` 仅文件内使用）。建议打 release 实机验证长公式回包。

## 修复"agents 聊天一有 AI 回复就闪退"+ 旧历史记录打开也崩（第四类根因：渲染库判断逻辑 + WebView 泄漏）

**现象**（用户再次反馈，与前三类不同）：现在只要 agents 聊天一出 AI 回复就闪退；**而且早期（引入渲染库之前）的聊天记录、只要其中包含 AI 回复，现在一点开也崩**。用户判断是"渲染库逻辑判断出错了"。

**根因分析**：
1. **提示词强制渲染标记**：`AgentOrchestrator.RENDERING_PROMPT` 旧版是"强制规范"——要求 AI **所有**公式用 `$...$`/`$$...$$` 包裹。于是 agents 回包（以及早期历史回包，都是在同款提示词下生成的）几乎**每条都塞满数学标记** → 客户端为每条标记都创建 WebView → 一有回复/一打开就同时存活大量 WebView → 闪退。这正是"早期历史也崩"的原因（旧回包本来就带满标记，渲染库只是后来才"接上"去渲染它们）。
2. **WebView 泄漏/无兜底**：`MathWebView`/`SmilesWebView` 的 `AndroidView` **没有 `onRelease { destroy() }`**，WebView 实例随 LazyColumn 复用/消息进出组合而泄漏累积；且创建失败（WebView 不可用/初始化异常）会**直接抛异常拖垮整个 Activity**，没有任何文本回退。
3. **行内数学正则过宽**：`splitInlineContent` 用贪婪的 `$...$` 正则，会把普通文本里的货币/变量（如 `$5 和 $10`）误判成公式，凭空创建 WebView。

**修复**：
- `ui/components/MarkdownRenderer.kt`：
  - `splitInlineContent` 正则改为**只识别受控的 `$smiles{...}`**，去掉行内 `$...$` 数学识别（行内数学改由 `$$...$$` 独立块处理）。消除普通文本误触发 WebView。
  - 新增全局 `MAX_ACTIVE_WEBVIEWS = 8`（`AtomicInteger` 计数）+ `createSafeWebView()`：WebView 创建**一律 try/catch**，不可用/超限/异常都返回 null → 调用方用 `TextView` 等宽纯文本回退，**绝不向上抛异常**。
  - `MathWebView`/`SmilesWebView` 加 `onRelease { if (view is WebView) { view.destroy(); count-- } }`：**离开组合即销毁**，根治泄漏累积。
  - 保留 `MAX_FORMULAS_PER_MESSAGE = 24` 单条上限（兜底极端长回包）。
- `agent/AgentOrchestrator.kt`：重写 `RENDERING_PROMPT` 为**"能力声明 + 按需使用"**——只告诉 AI 客户端**有** KaTeX/SmilesDrawer/JSON/CSV 渲染库，**用不用、怎么用由 AI 自己判断**，普通文本无需特殊处理。移除强制 `$...$` 指令（这步直接消灭了"每条回复都带数学标记"的源头）。

**关于"编排是否有问题"**：`ChatViewModel` 的编排是健康的——AI 回包通过 `StateFlow` **一次性 append**（无逐 token 重组风暴），`loadingStatus` 变化不触碰 `MarkdownText`。所以"编排"层面没问题，真正的病根是**提示词强制加渲染标记 + 渲染层判断过宽 + WebView 无销毁兜底**这一组合。

**验证**：`./gradlew compileDebugKotlin --offline` → BUILD SUCCESSFUL（EXIT=0）。建议打 release 实机验证：agents 长公式回包 + 打开早期历史会话。

## 最终诊断 + 根治：彻底禁用 WebView 渲染（第四次修复仍闪退后的终极方案）

**背景**：经过 4 轮修复仍闪退，用户反馈"修复好多次了都没解决"。重新梳理了从 sendMessage → AgentOrchestrator.execute → StateFlow.appendAssistant → LazyColumn recompose → MessageBubble → MarkdownText 的完整链路，确定编排（ChatViewModel StateFlow 一次性 append）和线程安全（无后台写 MutableState）都正确。

**结论**：Java try/catch 层已全覆盖但仍闪退 → 判定为**设备/系统级 WebView 原生崩溃**（native SIGSEGV / 渲染进程崩溃，try/catch 无法拦截）。这在部分 Android 设备/版本上是 WebView 的已知平台 bug。

**根治方案**：**全局禁用 WebView 渲染**。所有公式（`$$...$$`、`$smiles{}`）和化学结构式（```smiles/```tex 代码块）一律退化为 `FallbackFormula`（等宽纯文本 Compose Text）。公式内容仍然可读，只是不"美化"渲染——但 100% 不再闪退。

**具体改动**：
- `ui/components/MarkdownRenderer.kt`：
  - `MarkdownText`：`parseBlocks` 外层加 try/catch 兜底 + `noWebView` 标志驱动子渲染器放弃 WebView。
  - `ParagraphBlock`：参数从 `forceText` 改为 `noWebView`，Smiles/InlineMath 统一走 FallbackFormula。
  - `RenderedCodeBlock`：tex/latex/math 和 smiles/smi/mol 代码块改走 GenericCodeBlock。

## ★★ 真正的闪退根因：PatternSyntaxException（正则语法错误），不是 WebView

**通过 adb logcat 精准抓到的崩溃堆栈**：

```
FATAL EXCEPTION: main
java.util.regex.PatternSyntaxException: Syntax error in regexp pattern near index 18
\$smiles\{([^}]+)}
                  ^
    at go.examate.hyp.ui.components.MarkdownRendererKt.splitInlineContent
    at go.examate.hyp.ui.components.MarkdownRendererKt.ParagraphBlock
    at go.examate.hyp.ui.components.MarkdownRendererKt.MarkdownText
    at go.examate.hyp.ui.chat.MessageBubbleKt.MessageContent
```

**根因**：`MarkdownRenderer.splitInlineContent` 里的正则 `\$smiles\{([^}]+)}`，末尾 `}` 未用 `\}` 转义。Android 的 ICU 正则引擎（`android.icu.util.regex.PatternNative`）比标准 JDK 引擎严格，把未转义的 `}` 当作语法错误 → `PatternSyntaxException` 在 Compose 重组时未捕获 → Activity 闪退。

**为什么之前一直以为是 WebView 崩溃**：
- 错误 1：以为后台线程写 MutableState 导致 snapshot 污染 → 修了不动
- 错误 2：以为 WebView update 重载导致重组风暴 → 修了不动
- 错误 3：以为 WebView 原生 SIGSEGV 无法拦截 → 把 WebView 全删了也不动
- **真正原因**：一个未转义的正则字符。因为 `PatternSyntaxException` 是在 Compose 重组（`ComposeInternal`）中抛出的，堆栈里混了 Compose runtime/Bridge 等框架层调用，肉眼很难定位到应用自己的正则。

**教训**：闪退优先查 adb logcat（`AndroidRuntime` + `FATAL EXCEPTION`），不要凭直觉预判原因。Kotlin 正则里花括号 `{}` 在 ICU 引擎下必须成对转义——即使你认为 `}` 在不在量词语境中是字面量。

**修复**：`Regex("\\${'$'}smiles\\{([^}]+)}")` → `Regex("\\${'$'}smiles\\{([^}]+)\\}")`（末尾 `}` → `\}`）。

**附：本次顺带做的 UI 优化**：
- 移除顶栏"新对话"(+)按钮。
- 历史按钮从中文"历史"改为 `Icons.Filled.DateRange` 图标（避免长模型名时溢出）。
- 对话/Agents 切换从顶栏移到输入框下方，改为轻量文字切换（不再带图标背景的 pill 样式）。
- 空状态简化为仅一行"与 AI 开始对话"。

## 修复 Hsxs 登录根因 + 版本升级 1.05

**Hsxs 登录根因**: `getServiceTicket()` 返回 `Pair<String?, String?>`，但 Android 代码用 `val ticket = getServiceTicket(...)` 将整个 Pair 赋值给 ticket，序列化为字符串时变成 `(ST-xxx, https://...)` 而不是纯 ticket 值，导致 `validateLogin` 收到非法 ticket → 永远返回"ticket 或 service 缺失"。
